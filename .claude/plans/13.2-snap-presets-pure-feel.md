# 13.2 — Snap presets hold force / spring / damping only

Planning session 2026-08-23. Decisions settled with the user; build spec below.

## Problem

`SnapPresetSettings` already excludes `scaleRoot` / `scaleId` / `hidePitchLines`, but
presets still carry `enabled` (Snap) and `magneticEnabled`. Two consequences:

1. A "snap feel" preset can silently flip toggles the user set deliberately.
2. Two of the four built-ins carry *nothing but* those toggles — `builtin-free-draw`
   is `{enabled: false, magneticEnabled: false}` and `builtin-chromatic` is
   `{enabled: true, magneticEnabled: false}`. Neither holds a single physics value,
   so narrowing the type empties them outright.

The built-in names also advertise key/scale feel ("Chromatic 1/16", "Magnetic +
Diatonic") for settings that never touched key or scale.

## Decisions

**D1 — Drop both toggle-only built-ins; re-author the set.**
The Snap and Magnetic toggles sit two rows above the preset dropdown in the same
drawer, so those presets duplicated visible controls. The replacement set is
pure feel (below).

**D2 — Applying a preset force-enables Snap *and* Magnetic.**
The user's call: a preset click should always produce an audible change. Note the
gate in `computeComposeCursorPitch` is `st.snapEnabled && performContext &&
st.magneticEnabled` — magnetic needs *both*, so enabling only Magnetic would still
do nothing. Enabling is an **apply-time side effect, not a stored field**: the
preset object still holds only the three physics values. Toast when a load had to
flip a toggle, following the 10.5 `Record next Pass: Loop On` precedent.

**D3 — Starting values proposed here, tuned by ear afterward.**
The numbers below are derived from the physics constants and the two surviving
presets; they are a starting point for a hands-on pass, not final.

## Shipped built-ins

Ranges: force 0–1 step 0.05 (snapK = force × `SNAP_STRENGTH_MAX` 800, scaled by
well radius); spring 1–50 step 1; damping 0.25–15 step 0.25.

| Name | force | spring | damping | Feel |
|---|---|---|---|---|
| **Standard** | 0.85 | 50 | 6 | Matches the app's boot defaults, so the default state is nameable and reachable. |
| **Smooth Glide** | 0.25 | 30 | 13 | Just enough pull to feel a target going past without being caught by it, damped hard enough never to wobble. **Retuned after testing (2026-08-23):** shipped first as "Free Glide" at force 0, which was functionally indistinguishable from Snap off — a little force is what makes it its own feel. |
| **Loose Detents** | 0.45 | 30 | 5 | Gentle pull that lets the pitch sit between targets. Microtonal-friendly. Successor to "Magnetic + Diatonic" (0.7 / 22 / 2.5) with the key word removed. |
| **Pitch Lock** | 1.0 | 50 | 10 | Hard grab, quick settle, minimal overshoot. Successor to "Magnetic On-Pitch". |
| **Vibrato** | 0.9 | 18 | 1.5 | Strong attractor + loose spring + low damping = sustained undulation around a held target. The combination help.html already describes in prose but never shipped as a preset. |

Names describe magnet behaviour only — no key or scale words (the defect being fixed).

## Build

1. **`src/utils/snap-presets.ts`**
   - `SnapPresetSettings` → `Partial<Pick<SnapSettings, 'magneticStrength' | 'magneticSpringK' | 'magneticDamping'>>`.
   - Replace `BUILTIN_SNAP_PRESETS` with the five above (new ids; old ids are not
     persisted anywhere, see Migration).
   - `loadUserSnapPresets`: drop the `enabled` / `magneticEnabled` branches. Existing
     localStorage entries keep those keys; per-field validation ignores them silently.
   - `presetMatches`, `snapshotPreset`: three fields only.
2. **`src/main.ts`** preset-apply path (`snapPresetSelect` change handler)
   - Remove the `s.enabled` / `s.magneticEnabled` branches.
   - Before applying physics, force `store.setSnap(true)` / `store.setMagneticEnabled(true)`
     when either is off, and toast which one(s) it turned on.
3. **`help.html`** — rewrite the preset list, drop `strength`→`force` leftovers in
   preset descriptions, and state that loading a preset turns Snap + Magnetic on.

## Migration

`activeSnapPresetId` is in-memory only. Compositions persist snap *values*
(`comp.snap`), never a preset id, so retiring `builtin-free-draw` etc. breaks no
saved file — the dropdown re-derives its selection via `presetMatches`. User presets
in localStorage survive; their now-unknown keys are dropped by the existing
per-field loader. No schema version bump.

## Known wrinkle (accepted)

`presetMatches` now ignores the toggles, so with Magnetic off the dropdown can still
show a preset name whose physics values happen to match. Acceptable: the label
describes the stored feel, and loading it turns the toggles on anyway.

## Deliberately out of scope

Preset **export/import** — floated as the route for authoring defaults by ear
(tune in-app → export → promote into code). Not needed now that starting values are
proposed directly; revisit with 12.2's Import-settings verb if hand-tuning turns
into a repeated loop.
