# 8.24 — Pitch bend input (MIDI file import + live record)

## Context

SlideSynth's whole reason for existing is continuous pitch — notes are `BezierCurve` objects whose Y axis is a continuous float MIDI note, played by an `osc.frequency.setValueAtTime` lookahead scheduler. Yet the two MIDI ingress paths both throw away expressive pitch information:

- [src/export/midi-import.ts](src/export/midi-import.ts) reads only `setTempo` / `noteOn` / `noteOff` and emits a flat 2-point curve per note. Pitch bend events in the file are silently discarded — see comment at [src/audio/midi-input.ts:6](src/audio/midi-input.ts).
- [src/audio/midi-input.ts:54-64](src/audio/midi-input.ts) decodes only `0x90` / `0x80`. Status `0xE0` (pitch bend) is filtered out.

Pitch bend is the most natural fit for SlideSynth's curve model — every existing piece of the audio engine, the curve sampler, and the recording RDP simplifier already handles continuous Y. The work is entirely on the ingress side.

Decision: ship in **two PRs**. Import first (zero realtime risk, easy to validate against hand-crafted test SMFs), live record as a follow-up (needs hardware to verify).

## Phase 1 — MIDI file import reads pitch bend (PR #1)

### Approach

1. Build a **per-channel bend timeline** during a pre-pass over **all** tracks (Type-1 SMFs put bend on different tracks than notes). Map: `Map<channel, Array<{tick, value}>>`. Library `midi-file` returns `event.value` already zero-centered as signed `-8192..+8191` — do **not** subtract `0x2000`.
2. Sniff **RPN 0/0 (Pitch Bend Sensitivity)** during the same pre-pass. Track per-channel `bendRangeSemitones`, default `2`. RPN sequence is CC 101=0, CC 100=0, then CC 6 (MSB) gives semitones, CC 38 (LSB) gives cents/100. Many files don't emit RPN; fall back to `2`.
3. At each note's construction (today: [src/export/midi-import.ts:135-142](src/export/midi-import.ts), 2 control points), instead build a `RecordedSample[]` array:
   - One sample at `note.startTick` with `y = noteNumber + bendAt(startTick) * range / 8192`.
   - One sample per bend event with tick in `[startTick, endTick)` for that channel.
   - One sample at `note.endTick` with the final bend applied.
4. Convert ticks→beats using existing tempo conversion (the importer's current single-tempo limitation carries forward — flag as known-issue).
5. Feed the sample array through the **existing** `curveFromRecording` function at [src/model/curve.ts:472-505](src/model/curve.ts) — this gives RDP simplification + monotonic-X enforcement + auto-smooth handles for free, with the same anisotropic tolerances the live-record path uses (`0.03` beats, `0.15` semitones). No new simplifier code.
6. Add a **hard cap** of 256 control points per curve. Dense vibrato → `O(points)` cost in the audio scheduler's per-window iteration, and a 32-track project with thousand-point curves will be felt. If the cap trips, log a console warning with the curve's note + start beat.
7. Order events by `(tick, eventTypeOrder)` so a bend at the same tick as a note-off processes **before** the note-off — otherwise files that "reset bend on release" silently drop the trailing data.

### Files

- **[src/export/midi-import.ts](src/export/midi-import.ts)** — main work.
  - Add `BEND_RANGE_DEFAULT = 2` near line 24.
  - Pre-pass loop building per-channel bend timeline + per-channel RPN-derived range. Touch the event loop at lines 53-115; add `'pitchBend'` and `'controller'` (CC 6/38/100/101) cases.
  - Replace the 2-point curve construction at lines 135-142 with a sample-array → `curveFromRecording` path.
- **[src/model/curve.ts](src/model/curve.ts)** — likely no changes if `curveFromRecording` is already exported. If not, export it. Confirm the 256-point cap is enforceable from the call site (passing a max in, or a post-trim).
- **[BACKLOG.md](BACKLOG.md)** — add 8.24 entry under the MIDI section, check it off in the PR.

### Edge cases (handled in approach)

- Bend with no active note on channel: timeline records it; no curve emitted. Subsequent noteOn picks up current bend correctly.
- Bend before the first noteOn on a channel: per-channel bend init to 0; updates from tick 0 regardless of note state.
- Chord on one channel: each held note's curve independently slices the same bend timeline. Works because the timeline is keyed by channel, not note.
- Bend at same tick as noteOff: event-order tiebreak ensures bend lands inside the note's curve, not after.
- Centre reset at end of note: if previous bend was non-zero, the reset emits a final sample so the curve resolves to centre rather than ending bent.
- Tempo automation mid-bend: **not handled** in this PR — same limitation as the existing importer (only first `setTempo` consumed). Flag in PR description as a follow-up.

## Phase 2 — Live MIDI record bends the planchette (PR #2)

### Approach

1. Extend [src/audio/midi-input.ts](src/audio/midi-input.ts) `handleMessage` (line 54) to decode `command === 0xE0`. Add `onPitchBend(cb: (channel: number, value: number) => void)` to the `MidiInput` interface. Value is signed `-8192..+8191` (assemble as `((data2 << 7) | data1) - 0x2000`).
2. In [src/main.ts](src/main.ts) MIDI wiring (where `onNoteOn` / `onNoteOff` are subscribed), maintain `channelBend: Map<number, number>` of current bend value per channel. Default 0. Use hardcoded `BEND_RANGE_SEMITONES = 2` for live (no RPN sniffing on the wire — almost no controllers send it).
3. Per the design decision: **MIDI recording is not snap-affected**. The captured Y is `midiNoteNumber + (channelBend[channel] * 2 / 8192)`. The planchette visual also follows this bent Y — visual and recording stay coherent.
4. Wire-in point for capture: `tickComposeRecord` capture loop in [src/main.ts](src/main.ts) around line 2427. For each MIDI planchette (`voiceId.startsWith('midi-')`), substitute `note: midiNoteNumber + bendOffset` instead of `p.snappedWorldY`.
5. Wire-in point for visual: the planchette's `cursorWorldY` / `snappedWorldY` fields. For MIDI planchettes, keep the rendered Y in sync with the bent value so the user sees the bend.
6. **Loop wrap**: the per-channel `channelBend` map persists across loop wrap automatically (it's outside the planchette and the recording buffer). The existing `finalizeAllInFlightMidiVoices({ keepPlanchette: true })` pattern from PR #54 ([src/main.ts:2552-2560](src/main.ts)) needs no change — when fresh capture starts on the wrapped side, the first sample already reflects current bend.

### Files

- **[src/audio/midi-input.ts](src/audio/midi-input.ts)** — `MidiInput` interface (line 17), `handleMessage` (line 54). Update the deferred-scope comment at line 6.
- **[src/main.ts](src/main.ts)** — MIDI wiring (subscribe to `onPitchBend`), `channelBend` map, `tickComposeRecord` substitution at line 2427, planchette visual update for MIDI voices.
- **[src/types.ts](src/types.ts)** — possibly extend `PlanchetteState` with a `bendOffset` field (lines 148-163), or compute on the fly from the channel-bend map at render time. Probably cleaner to keep on the planchette so the renderer is stateless; trade-off is bend-state lives in two places.
- **[BACKLOG.md](BACKLOG.md)** — add 8.25 entry, check it off in the PR.

### Edge cases

- Bend non-zero at note release: fine — RDP keeps the trailing point, audio engine plays the offset pitch.
- Multiple notes held on same channel with bend: all planchettes for that channel share the bend offset (correct MIDI semantics; not MPE — document as known-not-handled).
- Bend received with no active MIDI planchette on that channel: just update channel-bend state. No-op on capture side.
- Bend across loop wrap: see (6) above. Per-channel state persists.
- MPE / per-note bend: out of scope. Flag for future.

## Shared concerns

- **No schema migration.** Bend folds into existing `BezierCurve.points`; the JSON shape is unchanged. `Composition` version stays at 2.
- **No audio-engine changes.** [src/audio/playback.ts](src/audio/playback.ts) and [src/audio/curve-sampler.ts](src/audio/curve-sampler.ts) sample whatever Y is in the curve.
- **No undo/history changes.** Import replaces composition wholesale; live record's history snapshot in `composeEngine.finalizeCurve` is unaffected.
- **MIDI export is out of scope.** Re-emitting bend from curves on save-to-MIDI is a separate, larger feature.

## Verification

### Phase 1 (import)

1. Hand-craft / find a small SMF with known bend. A monophonic 2-bar phrase with a half-bar slide of `±2` semitones is enough.
2. Import via File → Import MIDI. Confirm the resulting curve has multiple control points along the bend, not just two endpoints.
3. Play it. Compare against the source rendered by another DAW or synth — the audible bend shape should match.
4. Test a multi-channel SMF (Type-1) where bend events live on a different track than the notes. Confirm the cross-track per-channel timeline correctly applies bend to all channel-matching notes.
5. Test an RPN ±12 file (guitar bend range). Confirm the bend depth scales correctly.
6. Test a pathological file with thousand-event vibrato. Confirm the 256-point cap engages with a console warning, no UI hang.

### Phase 2 (live record)

Requires a MIDI controller with a bend wheel.

1. Arm a track for MIDI record. Hold a single note, push the bend wheel ±max. Confirm the planchette glides off the snap line as the wheel moves.
2. Stop recording. Inspect the committed curve — control points should follow the bend gesture.
3. Play the curve back. Audio should bend identically to the live performance.
4. Hold a note, bend, cross a loop wrap. Confirm two contiguous curves are produced (one ending at loop-out with current bend, one starting at loop-in with the same bend) — extends the 8.21 pattern.
5. Hold two notes on the same channel, bend. Confirm both curves capture the bend.

`npm run dev` → http://localhost:5187 (per BACKLOG.md housekeeping note).
