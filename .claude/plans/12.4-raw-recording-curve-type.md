# Raw-recording curve type (design exploration)

> Status: parked input to BACKLOG 12.4 (raw-take retention). Capture-only — no
> implementation. Written before the cents + lanes refactor, so line references
> and note-number units are out of date; the idea stands. Recovered from a stale
> worktree during BACKLOG 14.5.

## The problem

`curveFromRecording` ([src/model/curve.ts:472](src/model/curve.ts)) runs RDP
with anisotropic tolerances (`0.03 beats`, `0.15 semitones`) on the raw
`recordingBuffers` samples and replaces them with a Bezier anchor sequence
plus auto-smooth handles. RDP is destructive: the raw samples are dropped on
LMB release.

The simplification usually produces an editable curve that matches the
original gesture well. But small-scale fluctuations — micro-vibrato,
intentional pitch wobble, expressive jitter — fall below the RDP tolerance
and are erased. There's no way to preserve them, and no way to recover them
after the fact.

## The shape of the idea

Introduce a second curve type that stores the raw sample stream verbatim
(no RDP, no Bezier anchors, no handles). It renders as a polyline (or
piecewise-linear) and the audio engine plays it directly from the sample
array. It is **not** point-editable — that's the deliberate tradeoff, and
it's what saves the editor from drowning in thousands of anchors per take.

Convert-to-Bezier is a single action that runs the existing
`curveFromRecording` (or just the RDP + handle-generation halves of it) on
the raw samples and replaces the raw curve with an editable Bezier. The user
opts into editing destructively; before that, the raw data is preserved.

## Why a separate type, not an optional field

We discussed the alternative — give `BezierCurve` an optional
`rawSamples?: RecordedSample[]` field that gets stashed at record time and
re-used when "Simplify" runs. That approach doesn't solve the problem,
because **the audio engine still plays the simplified Bezier**, so the
small-scale fluctuations are still lost from playback. The user wants the
raw data to be *audible*, not just recoverable.

Once audio playback has to read from raw samples in some cases, you already
have a dual code path. Making it explicit in the type system is cleaner than
hiding it behind a nullable field.

## Cost

Plumbing, not algorithms. Memory and CPU are cheap:

- Recording buffer is capped at `recordingBufferMax: 3600`
  ([src/main.ts:2223](src/main.ts:2223)) — ~60s at 60fps. Raw samples are
  `{ beat, note, volume }` ≈ 24 bytes; a full take is ~86 KB.
- Render: polyline of 3600 segments is well under 1ms on canvas 2D.
- Audio: scheduling from a dense sample array is actually simpler than from
  a Bezier (no segment interpolation), though it generates more
  `AudioParam.linearRampToValueAtTime` calls. Pre-cull samples whose pitch
  delta is below an audible threshold if scheduling pressure shows up.
- History snapshots deep-copy curves; raw curves are larger but still
  measured in KB per take.

## Surface area (the real work)

Every place that iterates "the curves on a track" becomes a type union.
Quick inventory:

- [src/types.ts](src/types.ts) — `Track.curves` widens from `BezierCurve[]`
  to `(BezierCurve | RawCurve)[]`. New `RawCurve` type.
- [src/model/curve.ts](src/model/curve.ts) — new module siblings for raw
  curves (factory, bbox, sample lookup), plus a `convertRawToBezier()`
  that wraps `curveFromRecording`.
- [src/canvas/render-curves.ts](src/canvas/render-curves.ts) (or wherever
  curve rendering lives) — branch on type; raw curves render as a polyline
  with the same volume-color mapping but no anchor/handle overlays.
- Audio scheduler — branch on type. For raw, walk samples and emit
  `linearRampToValueAtTime` per pair; for Bezier, keep the existing path.
- Selection / hit-test — raw curves select as a whole only (no point or
  handle hits).
- Transform box — whole-curve translate, scale, octave-shift should work on
  raw curves (mutate sample positions). No per-point ops.
- Slice — either disallow on raw curves, or auto-convert to Bezier first
  (with a confirmation if data loss is implied). Easier path: disallow,
  surface a "Convert first" toast.
- Join — same: disallow or auto-convert. Probably disallow for v1.
- Smooth/Sharpen curve actions — N/A for raw; menu items disabled.
- History — `deepCopyPoints` analogue for raw samples (already trivially
  copyable since they're plain `{beat, note, volume}` objects).
- Project save/load — schema bump. Discriminator field on each curve
  (`type: 'bezier' | 'raw'`). Older project files default to `'bezier'`.
- MIDI export ([src/export/midi-export.ts]) — either sample the raw curve
  at the same cadence the Bezier exporter does, or convert-to-Bezier first
  internally. The export path already samples in time; raw is *easier* here.
- MIDI import ([src/export/midi-import.ts]) — unchanged; still produces
  Bezier curves via `curveFromRecording`.
- Cross-track curve selection, marquee select, copy/paste — type-aware but
  shallow.

None of these are hard individually. The cost is breadth, not depth.

## UX decisions to make before any code

1. **How is "record raw" enabled?**
   - Toggle in tool properties next to the existing record settings?
   - Per-track flag (some tracks are always raw)?
   - Global setting under a "Recording" pane?
   - Hot-modifier (hold Shift while recording for raw)?

2. **How does the user distinguish a raw curve visually?**
   - Different stroke style (thicker / dashed / slightly different hue
     ramp)? A small badge at one endpoint?
   - Selection state should be obviously different from a Bezier so the
     user doesn't expect anchor handles to appear.

3. **Where does Convert-to-Bezier (RDP) live?**
   - Right-click menu on a selected raw curve.
   - Optionally: auto-prompt the first time the user tries to enter Select
     mode and click into a raw curve. "This curve isn't editable. Convert?"
   - Keep the existing `curveFromRecording` defaults as the conversion
     defaults; expose tolerance later if needed.

4. **What operations should silently auto-convert vs. refuse?**
   - Refuse with a hint (recommended): slice, join, point-select, handle-drag.
   - Allow: whole-curve translate/scale/delete, copy/paste, MIDI export.
   - This keeps the "raw means immutable shape" mental model crisp.

5. **Does "Simplify Curve" (the user-facing RDP command from the earlier
   conversation) make sense for raw curves?**
   - Probably the same as Convert-to-Bezier — they're the same operation
     from the user's point of view: "turn this into an editable curve."
   - One menu item, two equivalent names. Pick one. Probably "Convert to
     editable" or "Convert to Bezier", not "Simplify", since the user said
     RDP is the operation that deserves the "Simplify" label.

## Open questions for the next pass

- **Does audio quality actually improve enough to justify this?** Worth
  recording a deliberate vibrato gesture, comparing the current Bezier
  playback to a raw-sample playback synthesized in isolation, and listening
  before committing to the full plumbing. If the answer is "marginal," the
  optional-field approach (raw stored, Bezier played) is cheaper.
- **Mixing raw and Bezier within a track:** if a track has both types, do
  the curves render visually consistent? The volume color ramp already maps
  per-segment in the Bezier path; raw needs the same mapping per sample-pair.
- **Recording buffer cap interaction:** the current `recordingBufferMax`
  ring-buffers old samples out when a take runs long. For raw recording,
  does the user expect *all* samples to be preserved? If so, the cap needs
  to either lift or grow when "record raw" is on. Decide before designing.
- **Project file size:** ten 60-second raw takes per project = ~3 MB of
  sample data. Fine in memory, possibly chunky on disk depending on the
  serialization. Consider a compact encoding (typed arrays, delta-coded
  beats) if file size becomes an issue.
- **Conversion is one-way (today):** once converted, the raw samples are
  gone. Should Convert-to-Bezier *keep* the raw samples on the new Bezier
  (the optional-field approach, layered on top) so the user can revert?
  This is a free upgrade once both types exist.

## What this doc is *not*

- Not a BACKLOG item yet — design is parked, not scheduled.
- Not a binding architecture choice — the optional-field alternative is
  still on the table if the audio quality difference turns out to be
  small.
- Not an implementation plan — when this is picked up, the next pass should
  produce a numbered plan doc with concrete file changes and a verification
  checklist, in the style of [.claude/plans/midi-arm-discoverability.md].
